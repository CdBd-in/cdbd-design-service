### ⭐ PPT `srcRect` = 클라이언트 지정 크롭
PPT 도형에 `<a:srcRect l/t/r/b>`(1/1000 %)가 들어 있다 → **클라이언트가 원하는 노출 영역**.
비크롭 원칙을 지키면서 그대로 재현하는 방법:
```
노출영역 ow = W*(1-l-r), oh = H*(1-t-b)
scale = 618/oh  (노출영역 비율 > 프레임 비율일 때 · 세로 fit)
rect.w = W*scale, rect.h = H*scale
rect.x = 190 - (노출영역 중심x_원본 * scale)   # 프레임 중앙에 노출 중심 정렬
rect.y = -(H*t) * scale
```
- `t` 또는 `b`가 **음수면 0으로 클램프** (안 그러면 프레임 상단에 빈 공간 생김 — 07이 해당)
- 프레임 비율(0.615)이 PPT 도형 비율(≈0.73)보다 세로로 길어 좌우가 더 잘린다 → 중심 정렬로 흡수

파싱: `unzip pptx` → `ppt/slides/slideN.xml` 의 `p:pic` 안 `a:srcRect` + `a:xfrm`. 도형 x좌표로 페이지 번호를 매칭.

### ⭐ 레이어(`block.layers[]`) 스키마 — 실측
```json
{
  "id": "<21자 nanoid, [A-Za-z0-9-_]>",
  "url": "<이미지 라이브러리 signed URL (plus-black/white.gif)>",
  "size": 10,
  "filename": "OUTER",
  "position": {"x": 74, "y": 23},
  "linkButton": {"data": {}, "link": {"href": "<UTM URL>", "openNewTab": true},
                 "type": "url", "phone": {}}
}
```
- `size` = **레이어 폭의 %** (10 → 380×0.1 = 38px 정사각)
- `position` = **좌상단 기준 %** (UI 「위치 X/Y」 슬라이더와 1:1)
- `filename` = UI 레이어 이름. 이번엔 **카테고리 대문자**로 통일 (`OUTER`, `TRENCH-COAT` …)

### ⭐⭐ Figma 마커 → CdBd position 환산 공식 (검증됨)
```
BOX = 380 * size/100          # size=10 → 38
X% = round( x_box / 380 * 100 )
     x_box = (마커x + 마커w)   … 마커가 우향(상품이 왼쪽)일 때
     x_box = (마커x - BOX)     … 마커가 좌향(상품이 오른쪽)일 때
Y% = round( (마커y - BOX/2) / 616 * 100 )     # 버튼 세로 중심 = 선
```
> **검증**: 사용자가 UI에서 직접 맞춘 P3 `BLOUSE`(X=74, Y=23)가 이 공식 결과와 **완전 일치**. 나머지 16개에 동일 적용.
>
> 방향(우향/좌향) 판정 = 선의 어느 끝이 배경인지. 작업파일 PNG에 선 양끝을 색 원으로 표시해 시각 확인하는 방법이 확실하다.

## E. 이번에 확인된 규칙

- **PPT `srcRect`는 클라이언트가 지정한 크롭 영역** — 화보 비크롭 원칙과 충돌하지 않는다. RECT의 위치·배율로 재현하면 "의도한 노출 영역 + 원본 비율 유지"를 동시에 만족.
- **CdBd 레이어 `position`은 Figma 마커 좌표에서 결정론적으로 환산 가능** (위 공식). 사용자 수동 입력값으로 교차검증하면 신뢰도가 확보된다.
- **텍스트/마커 색상은 요소가 실제로 얹히는 영역 명도로 개별 판단** — 페이지 단위 일괄 결정은 오답을 만든다(한 페이지 안에서 흑백 혼용이 정상).
- **Figma `rescale()`** 로 기존 규격 컴포넌트를 신규 규격으로 옮기면 텍스트·이미지가 비례 축소돼 편하다.
